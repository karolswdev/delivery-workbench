# WLA-25-06 - Notify the operator durably

- **Project:** work-log-automation
- **Phase:** 25
- **Status:** backlog
- **Depends on:** WLA-25-01, WLA-25-02, WLA-25-04, WLA-25-05
- **Unblocks:** WLA-25-09
- **Owner:** unassigned

## Problem

The moments that need a human are exactly the moments the human is not
watching: a checkpoint waits for a decision, a run reaches
`awaiting-certification`, a nudge budget exhausts into a blocked stop, a
pushed branch turns red after everyone moved on. Today those facts are
visible only to whoever happens to open the Workbench. Agent
Orchestrator persists notifications with unread state and
acknowledgement; Phase 20 already gave this project a Telegram surface
with per-person consent. This story joins the two: durable notification
facts, delivered over the existing consented channels, carrying
previews — never apply buttons.

## Scope

- **In:** notification facts derived from ledger and signal events
  (`checkpoint-pending`, `awaiting-certification`, `run-blocked` with
  reason, `nudge-budget-exhausted`, `ci-failed`/`changes-requested`/
  `merge-conflict` on observed branches) persisted append-only with
  unread/acknowledged state; `dw notifications [--json]` plus MCP/HTTP
  read and acknowledge surfaces; delivery through the existing Telegram
  layer under Phase-20 per-person consent, reusing the hook/push seam
  from the ccgram absorption; checkpoint decisions modeled as **typed
  request ports** absorbed from microsoft/agent-framework-go — each
  checkpoint declares its request and response schema, carries a
  correlation id, validates the response at runtime, and the pending
  request survives pause/resume/restart (WLA-25-08 owns the persistence
  seam); a Telegram checkpoint reply is only ever the *response
  document* to such a port — the actual approve/reject still crosses
  the existing token-bound `run checkpoint` boundary, and a stale or
  mismatched correlation id refuses.
- **Out:** apply buttons, argv, or consent tokens inside any outbound
  message; notification channels beyond the already-consented Telegram
  surface and local Workbench; email/push vendors; digest/summary
  content generated by an LLM in the delivery path.

## Acceptance criteria

- [ ] Every notification fact derives from a ledger or signal event by a
  pure rule, is persisted append-only with unread/ack state, and
  acknowledging is idempotent and receipted; deleting any cache changes
  no answer.
- [ ] Outbound messages carry facts, references, and the checkpoint
  preview document only — a content test proves no token, apply
  command, or third-party content body ever leaves the machine.
- [ ] Checkpoint request ports are typed: request and response schemas
  declared in the score, correlation ids unique per pending decision,
  malformed or stale responses refused with a recorded reason, and the
  accepted response applied only through the existing exact-token
  checkpoint boundary.
- [ ] Per-person consent gates every Telegram delivery exactly as
  Phase 20 contracted — an unconsented member in a group triggers
  nothing, re-verified by the existing consent tests extended to
  notification kinds.
- [ ] Unread notifications survive restart and list identically over
  CLI, MCP, and HTTP; the Workbench shows the same set with live
  updates via WLA-25-05.
- [ ] Silence is safe: with Telegram unconfigured or unreachable,
  notification facts still persist and surface locally, and delivery
  failure is a recorded, retried-with-ceiling outcome, never a crash or
  a silent drop.

## Test plan

- **Unit:** derivation rules, ack idempotency, correlation/schema
  validation, outbound content-exclusion assertions.
- **Integration:** fixture run to `awaiting-certification` with a
  scripted checkpoint answered through the typed port; unreachable
  channel red path; consent-gate red path.
- **Manual / device:** receive a real checkpoint-pending message on
  Telegram, reply with a decision, and watch the token-bound approval
  land in the Run view — then repeat after a daemonless restart to see
  the pending request republished.

## Notes / open questions

The typed-port grammar deliberately makes "answer a checkpoint from the
phone" a *document* flow rather than a button flow: the phone supplies
the decision content, the rails supply the authority. Whether
`ci-failed` on branches with no associated run should notify by default
or require opt-in per project is open for the contract story.
